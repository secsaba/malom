# The rules engine and search have no UI dependencies

`src/engine` (rules, legal moves, mill and capture logic, phase transitions, endings) and `src/ai` (search and evaluation) import nothing from React, the DOM, or the strings module. They are pure TypeScript over plain data. `src/ui` depends on them; they never depend on it. A lint rule fails the build if that direction is violated.

`src/session` — the game session facade, the only thing `src/ui` plays the game through — sits on the engine's side of that boundary and under the same lint rule. (`src/ui` still reads the board itself, for the points and lines it draws; what it never does is reach past the facade to work the rules.) It is the module the interface is most tempted to let leak: it is where a Hungarian sentence or a `localStorage` call would feel natural. It returns the phase, the pending capture and the legal points as data instead. What it does not hold is how a move is played: it turns the taps an interface deals in into whole moves and hands those to the engine. The rules it does keep are the ones about a move being assembled — which piece has been picked up, and whether a capture is still owed — because picking a piece up is a step a player can take back, and that is a rule rather than a detail of any one interface.

`src/opponent` — the computer as a player: its four difficulties, how deep each of them looks, how long its move is held back, and the Web Worker it thinks in — is the fourth module under the rule. How deep is the whole of how far it looks: there is no clock in the search, because an opponent bounded by time answers one thing on a desktop and another on a phone, and the strongest difficulty has to be the fixed thing a learner measures themselves against. The worker is where the boundary is cashed in rather than where it is breached: the thread runs the same search everything else runs, and holds no rules of its own, so nothing about the computer's play has to be tested through a worker to be tested at all. One thing there is browser-facing all the same, and only one — the `new Worker(…)` that starts the thread. It is confined to a single adapter, `src/opponent/search-thread.ts`, which the lint rule names as the one place allowed to start a thread and holds to every other restriction; `Worker` is forbidden everywhere else behind the boundary, so a second way onto a thread cannot appear quietly. That adapter offers a search and nothing more, which is why the thread is one thread: the computer's move and the player's hint are the same search asked a different question, and a second worker would be a second copy of the engine.

`src/teaching` — what the engine has to say about a move rather than which move to play: the hint it would play, the grade a move earned, the patterns it detected in it and the reason those come to — is the fifth module under the rule, and the one where breaking it would be least visible and most damaging. Its output ends up as a sentence, so the temptation is to word it here; a reason written in Hungarian in this module is a reason no English translation can reach, and grading that reported text instead of data could not be tested against the position that produced it. It hands back moves, evaluations and named patterns, and `src/ui` says them out loud: a pattern crosses the boundary as `"fork-created"` and becomes a Hungarian sentence on the other side of it. It also holds no engine of its own: hints run at full strength (ADR-0001) by reading the strongest difficulty's depths off `src/opponent/difficulty` rather than keeping a second table that could quietly fall behind it.

The draw conditions are part of those rules and live in `src/engine/game`, the module that plays a whole game rather than answering questions about one position. Neither repetition nor the fifty-move count is a question a single position can answer, which is why they are not in `src/engine/position`; but they are equally not the facade's, because the search has to see them too. A search that scored a drawn line as a win would recommend playing into it, and hand the learner a move that throws away a game. Both the facade and the search therefore play their moves through the same module, and there is only one copy of what ends a game.

## Consequences

The rules are unit-testable without rendering anything, and the search can run inside a Web Worker without dragging UI code across the boundary — the reason it can stay responsive at high difficulty. It also means the engine cannot produce user-facing text: it returns patterns and evaluations as data, and `src/ui` turns those into Hungarian or English sentences. The lint rule is the load-bearing part of this decision. Without enforcement the boundary erodes on the first convenient import, and by then the worker and the tests have both quietly broken.
